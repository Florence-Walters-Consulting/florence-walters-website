# Migration decisions

Plan: `~/.claude/plans/there-s-no-hosting-done-twinkling-gadget.md`. Branch: `next-migration`.

## Phase 1
- **New app lives in `web/`, not repo root.** The plan said to move legacy code into `legacy/`. Instead the legacy Vite + PHP app is left exactly where it is so it keeps running for side-by-side comparison, and Vercel just uses `web/` as its root directory. Delete the legacy folders after cutover.
- **Separate local DB `florencewalters_next`** for the new app (imported from `florencewalters.sql`, then `web/db/migrations/001_cleanup.sql`). The legacy app keeps using the untouched `florencewalters` DB.
- **Original dump is never edited.** Cleanup (InnoDB, slug indexes, unique subscriber email) is a separate migration.
- **Drizzle schema** was introspected from the migrated DB (`web/src/db/schema.ts`), not hand-written. Column types (varchar dates, "Yes"/"No" flags) are kept as they are.
- **Cache Components is on** (create-next-app default in Next 16.4). Data queries will use `'use cache'` + `cacheLife` + tags so admin edits can revalidate public pages.
- **`npm audit` reports 5 high findings**, all in dev-only lint tooling (`braces` via `eslint-config-next`). Not fixed: the suggested `--force` fix downgrades `eslint-config-next` to v14.

## Phase 2
- **CSS is copied byte-for-byte** into `web/src/assets/` and imported in the original order in `app/layout.tsx`. Two deliberate non-CSS changes: skipped the unused Bootstrap JS, Swiper plugin and count-down side-effect imports (no component uses them); `bootstrap-select.min.css` was never imported so it was not copied.
- **Tailwind runs without Preflight** (`app/globals.css` imports only theme and utilities, in CSS layers), so it can't reset the Bootstrap look. Unlayered legacy rules always win over Tailwind utilities.
- **Satoshi font:** the remote `@import url(fontshare…)` in `fonts.css` is silently dropped by the Next bundler (it was no longer the first rule in the combined CSS), which made text fall back to Arial. The same URL is now a `<link>` in `app/layout.tsx`, and the `@import` line in the copied `fonts.css` is replaced by a comment. Verified with Playwright that Satoshi loads in both apps.
- **Plain `<img>` is kept** (ESLint rule `no-img-element` is off) so markup matches what the legacy CSS styles. Uploaded images are already resized WebP.
- **Local images:** `web/public/site_img` is an untracked symlink to `../site_img`. In production images come from `NEXT_PUBLIC_IMAGE_BASE_URL`.
- **Header/Footer ported 1:1.** `NavLink` active-state rule reproduced with `usePathname` (`/` exact, others by prefix). Footer is a server component (services list from the DB, cached 1h, tag `services`); only the newsletter form is client-side. The form posts to `/api/newsletter/subscribe`, which is built in Phase 4 (it does not exist yet, so subscribing fails until then).
- **ErrorBoundary:** legacy printed the raw error and component stack to visitors in red. Replaced by `app/error.tsx` with a generic message and retry button.
- **`figma-home.css` Figma URL:** it only sets the background of `.fwc-hero`, and `SlideShow` overrides that background inline with an uploaded image, so the dead URL has no visible effect. Left unchanged.
- **Port 3000** on this machine is used by another process (not ours); the Next dev server for comparison runs on 3100.

## Phase 3
- **Data pages are server components** reading the DB through cached queries (`web/src/db/queries/*.ts`, ported 1:1 from the PHP SQL: same columns, joins, ordering, limits). Client components only where needed: Swiper (hero, partners), FAQ accordion, blog toolbar/pagination, the three forms.
- **Blog filters/search/pagination are now URL-driven** (`/blog?category=3&search=risk&page=2`) instead of hidden React state, so results survive refresh and can be shared. Same 350ms search debounce, same markup/classes. Verified against the legacy API JSON (list order, category filter, search, prev/next/related).
- **Randomised content:** the PHP used `ORDER BY RAND()` for partners and testimonials on every request. Results are now cached for 1h, so partners are shuffled in the browser after hydration; the 4 testimonial avatars in the CTA are fixed per cache refresh (no longer random per visit).
- **Swiper is pinned to v12** (legacy major) and rendered behind `<Suspense>` with the legacy loading placeholders (`fwc-hero-loading`, `partners-loading`): Swiper reads the current time during render, which Next 16 forbids in the prerendered shell.
- **`partialPrefetching: false`** in `next.config.ts`. With it on, the first request to an unlisted slug returned HTTP 200 (streamed not-found UI); off, it is a real 404 on every request. Revisit if the option becomes mandatory in the next major.
- **Contact form timestamp** (`formStartedAt`, used by the API's anti-bot timing check) is set after mount; setting it during render froze it at build time and would have blocked every submission.
- **Dates** are formatted in UTC (stored values are plain `YYYY-MM-DD`), which avoids a one-day shift for visitors west of UTC. Legacy formatted in the browser's time zone.
- **Titles/metadata:** static pages keep the legacy titles ("About Us", "Insights", ...). Blog and service pages now use the real heading as the title and the preamble as the description (legacy derived a title-cased slug). No new marketing copy.
- **404:** unknown blog or service slugs return a real 404 page (`app/not-found.tsx`, with minimal new text: "Page not found" / "The page you are looking for does not exist."). Legacy rendered a blank page for unknown service slugs.
- **Not ported:** `components/Testimonials.jsx` (not used by any page), the auth context, `formatPrice`, and the unused service hook. `PageHeader`'s ignored `image` prop was dropped.
- **Kept as is:** nested `<main>` on the assessment/consultation pages (the legacy CSS targets them); all admin-authored HTML rendered with `dangerouslySetInnerHTML` (FAQ answers, hero text, testimonial and blog bodies), as before.
- **Env:** the "scheduler not configured" notice on the assessment result page named `VITE_DISCOVERY_CALL_URL`; it now names `NEXT_PUBLIC_DISCOVERY_CALL_URL`, the variable the new app reads. Dev `.env.local` uses Google's public reCAPTCHA *test* keys (always pass); production needs a real key pair.
- **Forms** post to `/api/contact`, `/api/business-assessment`, `/api/paid-consultation` and `/api/newsletter/subscribe`. These routes are Phase 4, so submitting any form returns 404 until then. Validation, wizard steps and the conditional questions were tested; submission was not.

## Phase 4
- **Four route handlers** (`web/src/app/api/{contact,paid-consultation,business-assessment,newsletter/subscribe}/route.ts`) replace the PHP endpoints, with the same JSON shape (`{success, data, message}`), same validation rules, same error messages and the same email content. Validation is Zod (`web/src/lib/forms/*`); shared pieces live in `web/src/lib/` (`api-response`, `rate-limit`, `request-guards`, `recaptcha`, `mailer`). Non-POST requests get Next's automatic 405.
- **Email via nodemailer over SMTP**, configured with `SMTP_HOST/PORT/USER/PASSWORD`, `MAIL_FROM`, `MAIL_TO` (see `.env.example` for the Microsoft 365 values: `smtp.office365.com`, port 587 STARTTLS). With `SMTP_HOST` unset (local dev) mail is built but not sent; `next dev` also prints the full message so it can be inspected. The legacy PHP set `Host=localhost, Port=25` and never called `isSMTP()`, i.e. it used the server's local mail transfer agent, not the mailbox.
- **Microsoft 365 risk:** Microsoft is retiring basic-auth SMTP for client submission. Per the January 2026 revision of Message Center post MC786329 (found via a secondary source, not checked in this tenant), basic auth keeps working until it is **disabled by default for existing tenants at the end of December 2026** (admins can re-enable it), with final removal announced for later in 2027. Also needed: SMTP AUTH enabled on the sending mailbox, and no MFA/conditional-access rule blocking it. If it breaks, the options are OAuth2 SMTP (nodemailer supports it), Microsoft Graph `sendMail`, or a different sender. Not tested against a real tenant: no credentials were available.
- **Fixes to legacy bugs** (the legacy forms could not work): (1) `paid-consultation` and `business-assessment` sent an undefined `$secret_key` to Google, so reCAPTCHA always failed; all forms now share one verifier. (2) The contact page sent `formStartedAt` but the PHP only read `form_started_at`, so every contact submission was rejected as "too fast"; both spellings are accepted. (3) Stale `omoniposofela` default hostnames/origins are gone.
- **Additions the legacy API did not have:** rate limits on the consultation, assessment and newsletter endpoints (6 per 10 min and 30 per day per IP, plus a global cap; newsletter 10/10 min and 40/day); the Origin check now covers all four endpoints, not only contact (same-origin always allowed; extra origins via `FORM_ALLOWED_ORIGINS`).
- **Rate limits are per server instance** (in memory), whereas the PHP stored counters in a temp file on one server. On Vercel each warm instance counts separately, so this slows bots but is not an exact global limit. An exact limit needs a shared store (Upstash Redis free tier); not added: needs your OK.
- **reCAPTCHA hostname check** is skipped unless `RECAPTCHA_ALLOWED_HOSTNAMES` is set. Set it to the production domain(s). Dev uses Google's public test keys (hostname `testkey.google.com`).
- **Client IP** comes from `X-Forwarded-For`/`X-Real-IP` (Vercel and normal reverse proxies set them). The legacy code only trusted that header from a configured list of proxy IPs.
- **Newsletter** relies on the unique key added in `001_cleanup.sql` for duplicate detection (MySQL error 1062), matching what the PHP intended.

## Phase 5: admin
Everything the legacy `admin7362/` did for the 10 live modules, rebuilt under `/admin` in `web/src/app/admin/`. Leftover shop pages (products, orders, menu, delivery, exchange rate, users, applications, announcement slider, projects, gallery, comments, categories) were dropped, as agreed.

### Structure
- **Route groups:** `(site)` holds the public pages with the legacy CSS, header and footer; `/admin` has its own layout with its own CSS (Tailwind *with* its normal reset). The admin therefore gets none of the public site's Bootstrap/brand CSS and vice versa. A single root layout is kept (multiple root layouts would need the experimental `globalNotFound` flag). `not-found.tsx` carries its own site chrome for unmatched URLs; `(site)/not-found.tsx` covers `notFound()` calls inside public pages.
- **Per-module layout:** `db/admin/*.ts` (Drizzle queries only) → `actions.ts` (auth, Zod validation, file handling, cache refresh) → `page.tsx` (list + modal forms). Shared pieces: `components/admin/*` (dialog form, delete confirmation, image field, Tiptap editor, toasts, nav) and `lib/admin/*` (action wrapper, schemas, uploads, sanitising, slugs).
- **Modal forms everywhere** (one pattern). Consequence: the blog list sends each post's body to the browser for its edit form. Fine for this site's size; if posts grow into the hundreds, switch the blog and services editors to separate pages.

### Security (all new; the legacy admin had none of these)
- **Legacy problems found:** none of the legacy admin endpoints (`admin7362/ajax/*.php`) checked that the caller was signed in, so anyone who knew a URL could edit or delete content; most upload handlers saved files under whatever extension the client claimed with no type check (arbitrary file upload); the login compared plaintext passwords.
- **Login:** username + password, bcrypt (cost 12). Plaintext legacy passwords are **not** accepted. Set a password with `npm run admin:set-password -- <username>` (hidden prompt, or `ADMIN_PASSWORD` env for automation; `--create --name --email` to add an admin). Unknown usernames take the same time as wrong passwords.
- **Session:** signed JWT in an HttpOnly, `SameSite=Strict` cookie scoped to `/admin`, 12 h, `Secure` in production. Needs `SESSION_SECRET` (≥32 chars).
- **Authorization is checked on the server every time:** every page re-verifies the cookie *and* that the admin row still exists; every Server Action runs through `runAdminAction()` which does the same before touching anything. `proxy.ts` is only an optimistic redirect. Server Action calls pass through the proxy on purpose so an expired session shows a clear message in the form instead of a generic error screen.
- **Brute force:** only *failed* sign-ins count (5 per IP+username / 10 min, 20 per IP / 10 min, 30 per username / hour), so normal logins never lock anyone out and one person guessing cannot lock the real admin out from another IP. In-memory per server instance (same caveat as the form limits).
- **Uploads:** type is decided from the file's content (sharp), never its name or declared type; only JPG, PNG and WebP; 5 MB max; random file names; extension chosen from the detected type; folder and name are whitelisted before touching disk. Tested: a PHP file named `.jpg` and an SVG containing a script are both rejected and nothing is written.
- **HTML hygiene:** rich text and the slider's heading/paragraph are sanitised before saving (scripts, event handlers and `javascript:` links removed), because the public pages render them as HTML. The `services` body keeps `class`, `section`, `details` etc.
- **Not enforced:** `admin_type` roles (the table has one `superadmin`); every admin can do everything, as before.

### Behaviour changes vs the legacy admin
- **Blog category** cannot be deleted while posts use it (legacy allowed it and orphaned the posts).
- **Slugs** for blog posts and services are made unique (`-2`, `-3`...); legacy silently allowed duplicates, where the public site would show the first match. Headings with no letters or numbers are rejected.
- **Blog cover images:** same as legacy (centre-crop to 800×600, WebP quality 80). **All other images** are kept as uploaded (legacy did the same) but validated; the stored extension now follows the real type.
- **Replacing/deleting** an image deletes the old file *after* the database points at the new one, so a failure never leaves a broken reference. Images embedded in rich text are deleted when removed from the text or when the item is deleted (as before).
- **Rich-text editor:** Summernote (and its grid plugin) replaced by Tiptap (free, MIT). It cannot represent the Bootstrap-grid markup Summernote-grid produced, so the `services` body (which uses `section`, `details`, classes) is a plain HTML box instead; blog, FAQ and testimonial bodies in the data are simple (`p`, `h3`, `ul`, `strong`...) and round-trip cleanly. Pasted `data-start`/`data-end` attributes (from an AI chat tool) are dropped on the first edit; harmless.
- **Testimonials:** new ones default to "shown" (as legacy); the form now also lets you hide one.
- **Team link:** must be an http(s) address (legacy accepted anything, including `javascript:`).
- **Other images:** replace-only, as legacy.
- **Subscribers:** list and remove (legacy had no export either).
- **Forms keep what you typed** after a validation error (React 19 would otherwise reset a form after any Server Action, even a failed one), so dialogs are submitted by hand.
- **Embedded editor images** are saved under `summernote/` as before (the folder name is kept so existing content paths still work) and uploaded through `/admin/upload-image` (under `/admin` so the session cookie, scoped to `/admin`, is sent).

### Storage (important for hosting)
Uploads go through `lib/storage.ts`. Only the **local disk** driver exists (development: writes to the repo's `site_img/`, or to `LOCAL_UPLOAD_DIR`). On Vercel files cannot be kept on disk, so **uploads will not work in production until the object-storage driver is added in Phase 6** (needs your choice of Vercel Blob or Cloudflare R2). Stored URLs keep the `/site_img/<folder>/<file>` path shape so the embedded-image cleanup keeps working with a remote driver.

## First real deploy attempt (user, 2026-10-11): lock-file failure
- **Symptom:** `deploy.sh` stopped at `npm ci` on the server: "package.json and package-lock.json are not in sync … Missing: @emnapi/runtime … from lock file".
- **Cause:** the lock file had been written by npm 11 (developer Mac, Node 24); the server runs npm 10 (ships with Node 22), which is stricter about optional platform packages. Reproduced locally with `npx npm@10 ci --dry-run` (fails) vs npm 11 (passes).
- **Fix:** regenerated `web/package-lock.json` with npm 10 (`npx npm@10 install --package-lock-only`; +9 entries). Verified `npm ci --dry-run` passes on both npm 10 and 11, and rehearsed the server's steps (clean `npm@10 ci` + `npm run build`) in a scratch copy: success.
- **Prevention:** `deploy.sh` now runs `npx npm@10 ci --dry-run` before contacting the server and explains the fix if it fails.
- **Also:** `deploy.sh` and `first-data-load.sh` reuse one SSH connection (password asked once instead of three or four times).
- **Unexplained, harmless warning:** rsync printed "cannot delete non-empty directory: web/public" and "…: web". That means the server has a folder `/var/www/fwc/web/web` that the laptop does not (rsync could not delete it because it holds protected files). Most likely a nested copy from an earlier manual `rsync` of `web` without the trailing slash. Not confirmed (no server access); the user was asked to list the folder.

## Second deploy attempt: `sharp` cannot run on the Namecheap VPS CPU
- **Symptom (user's server):** install and compile passed, then `next build` failed while collecting `/admin/upload-image`: "Could not load the sharp module using the linux-x64 runtime. Unsupported CPU: Prebuilt binaries for Linux x64 require v2 microarchitecture … WebAssembly.Module(): Wasm SIMD unsupported".
- **Cause:** the server's virtual CPU is too old/generic for `sharp`'s prebuilt libvips (needs x86-64-v2: SSE4.1/4.2, POPCNT). The WebAssembly fallback also needs SIMD, which needs SSE4.1, so the CPU likely lacks that too. Not yet confirmed by reading `/proc/cpuinfo` on the server.
- **Made the site independent of it:** `sharp` is now imported lazily (`lib/admin/uploads.ts`). Previously a top-level import meant the build crashed and any admin page importing it would crash at load. Only uploads need it; the public site does not use it at all (plain `<img>`, no `next/image`).
- **Verified by simulation** (installed `sharp` with its native binaries removed so `require('sharp')` throws, as on the server): build passes; public pages return 200; admin dashboard and the blog/team/FAQ admin pages load; an upload returns HTTP 422 with a clear message and writes nothing.
- **Visibility:** `deploy.sh` runs `web/scripts/check-sharp.cjs` on the server after each deploy and prints "image uploads: OK" or a clear WARNING. README troubleshooting row added, with a CPU-flags check.
- **Not fixed yet:** image uploads on that server. Options, in order: (1) ask Namecheap support for a modern virtual CPU type (host-passthrough / x86-64-v2+); (2) another provider with modern CPUs; (3) a code change to a processing library with no SIMD requirement (pure-JS/WASM-without-SIMD), larger and slower, untestable here without that CPU; (4) pinning an older `sharp` (<0.33, generic x86-64 binaries), which carries older bundled libraries. Decision pending the server's CPU flags.
- **Also learned:** `deploy.sh` runs lint, so the lint error in the new check script would have blocked the deploy; fixed (the script intentionally uses `require`).

## Third deploy attempt: uploads no longer need a native image library (supersedes the "sharp loaded lazily" stopgap above)
- **Diagnosis (user's server):** `model name: QEMU Virtual CPU version 2.5+`, and none of `sse4_1`, `sse4_2`, `popcnt`, `avx2` are present. A generic virtual CPU: `sharp`'s prebuilt libvips (needs x86-64-v2) cannot run, and neither can its WebAssembly fallback (needs SIMD, i.e. SSE4.1).
- **Decision:** remove `sharp` from the project and do image *processing* in the admin's browser; the server only *validates*. This works on any processor, needs no support ticket or provider change, removes a native dependency from every deploy, and reduces server load. Reversible: on a server with a modern CPU, `sharp` could be added back by changing `saveImage()` in `lib/admin/uploads.ts` (nothing was committed to git, so there is no history to restore from; this paragraph describes the old behaviour: it cropped and converted server-side and decoded the file fully).
- **Server (`lib/admin/uploads.ts`):** decides the type from the file's first bytes (JPEG, PNG, WebP only; no SVG/GIF/other), reads the dimensions with `image-size` (pure JavaScript, MIT, no dependencies) to prove it parses, rejects more than 12,000 px per side or 60 megapixels, enforces the 5 MB limit, stores under a random name with the extension from the detected type. Blog covers (`kind: 'exact'`, 800 × 600) are refused unless they are exactly that size.
- **Browser (`components/admin/ImageField.tsx`, `crop` prop used by the blog cover):** centre-crops to exactly 800 × 600 on a canvas and encodes WebP quality 0.8 (JPEG 0.85 with a white background in browsers that cannot encode WebP, such as older Safari). Source photos up to 25 MB are accepted for cropping because only the small result is uploaded; images that are not cropped keep the 5 MB limit. The form blocks submitting while the image is still being prepared. EXIF rotation is honoured by `createImageBitmap`.
